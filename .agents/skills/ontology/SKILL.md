# ontology — 지도 만들기 · 고치기

목적: 코드를 짜기 전에 «무엇을 확인해야 하고 · 무엇을 만들고 빼며 · 데이터가 어떻게 이어지나」를 한 장에 적는다.
늦게 발견하면 비싼 함정(같은 대상이 두 줄 · 빈칸이 뜻을 가짐 · 하나로 안 정해지는 연결 · 분모 착각)을 처음에 «확인할 것」으로 꺼낸다.

- 양식: docs/ONTOLOGY.md · 채운 예시: docs/examples/ONTOLOGY_ref_1.md(데이터 과제) · ONTOLOGY_ref_2.md(데이터 없는 서비스 과제) — 처음 쓰기 전에 과제에 가까운 쪽 하나를 읽는다
- 위 네 상자(확인할 것 · 0 한눈에 · 만들 것 판정 · 1 README 풀이)는 **유저가 읽는다** → 쉬운 말 · 짧게. 2 ~ 9번은 **AI 가 읽는다** → 말로 풀어 자세히, 숫자는 🔢 줄에 따로
- 초안 목표 시간: 10분. 완벽보다 «확인할 것」을 빨리 꺼내는 게 먼저다

## 1. 초안 — 과제를 받은 직후

**1-1. 재료 모으기** — 루트 README · 제공 자료 폴더(uploads 등) 파일 목록 · API 명세. README 에 개인정보 · 비밀값으로 적힌 열 이름을 먼저 찾아 둔다

**1-2. 데이터 세기 — 눈으로 훑지 말고 센다**
- CSV: python3 scripts/ontology/profile.py 파일1.csv 파일2.csv --hide 개인정보열 — 이름 · 연락처 같은 열은 알아서 숨긴다(확실히 아니면 --show). 출력은 통째로 붙이지 않고 필요한 숫자만 🔢 줄로
- «못 읽음」 · CSV 아님(엑셀 · JSON · API 응답) → 짧은 코드로 같은 항목을 센다: 열마다 빈칸 수 · 값 종류(12개 이하면 전부와 개수) · 숫자 범위 · 날짜 범위 · 형식 · 시간대 · 파일 안 순서 / 구별 기준 후보(혼자 안 겹치는 열 · 둘을 합치면 안 겹치는 짝 · 몇 줄만 겹치는 짝과 그 줄 번호) · 큰 파일은 앞부분 표본이라고 적는다
- API: 명세의 응답 예시로 채운다(근거 명세) · 키가 있으면 한 번 호출해 실제 값도 센다 · 없으면 확인할 것으로 · 찔러보기는 5절 «API 체크»
- DB: 표 · 열 · 제약은 5절 «DB 체크» 로 센다
- **데이터 없는 서비스 과제**: 2 ~ 9번 대부분이 «해당 없음」이다. 칸을 지우지 말고 왜 없는지 한두 줄 · 대신 확인할 것 · 만들 것 판정이 본체다(ref_2)
- **기존 코드 저장소** — 파일을 다 읽지 않는다
	- 정찰 6항목: 패키지 목록(requirements · package.json) · 프레임워크 · 진입점 · 상위 2단계 폴더 · 설정 · 테스트 위치 → 요청 하나를 진입점 → 입력 검사 → 업무 처리 → DB 까지 따라간다 → 결과는 docs/README.md 구조표
	- 지도에: 대상 = DB 표 · 요청 / 구별 기준 = 중복 금지 설정(UNIQUE) · 요청 구별 키(없으면 그 자체가 확인할 것) / 경우 = 상태 값과 그 값을 정하는 코드 위치(파일 · 함수) / 출처 = .mcp.json · .env.example 의 서비스 · 키 이름(값 제외 · 키가 필요하면 바로 확인할 것)
	- 업무 규칙은 코드에서 짐작하지 않는다 — 코드에서 읽은 것은 근거 [코드] «지금 이렇게 동작한다» 일 뿐(기존 코드가 버그일 수 있다) → 규칙 칸에는 추정 + Q 번호
	- 정본 순서: 업무 사실은 담당자 답 → 루트 README → 저장소 문서(PRD · ARCHITECTURE 등) → 기존 코드 · 과제 지시(제출물 · 범위)는 루트 README · 부딪히면 혼자 고르지 말고 확인할 것에

**1-3. README 문장 풀이(1번)** — 요구가 담긴 문장을 **전부** 원문 그대로 옮긴다(유저가 원문을 안 읽어도 내용이 보이게) · «어디로」와 «지도에 적은 곳」을 붙인다
- 판정 순서(처음 «예」인 곳): 따로 이름 붙어 셀 수 있나 → 대상 / 둘이 어떻게 이어지나 → 연결 / 값이 될 수 있는 경우인가 → 경우 / 대상 하나를 설명하는 값인가 → 정보 / 계산해서 나오는 숫자인가 → 계산 / 늘 지킬 조건 · 금지인가 → 규칙 / 어디서 받나 → 출처 / 만들 결과물 요구인가 → 지도 밖(결과물 — 만들 것 판정 · ADR) / 일하는 방식인가 → 지도 밖(작업 방식) / 뜻이 둘로 읽히거나 «사람마다 다르게 센다」 같은 기준 없음 신호인가 → 확인할 것
- 한 문장이 여러 곳에 걸리면 모두 적는다

**1-4. 결과에서 거꾸로 따라가기** — 최종 결과 한 줄을 적고 «손으로 센다면 무엇을 세나」를 거꾸로 따라간다(결과 ← 계산 ← 대상 ← … ← 파일 · API) → 5번 «가는 길」 · 그 길의 이름을 2 ~ 9번에

**1-5. 2 ~ 9번 채우기(AI 용)**
- 말로 풀어 쓴다 — «로트 하나에 웨이퍼 다섯 장」 처럼. 개수 · 줄 번호 · 바뀌는 폭 · 손계산 같은 숫자는 칸 끝 🔢 줄에 모은다. 세지 않은 칸은 «아직 안 셈」
- 줄 끝 근거 표시 · 확신 없으면 추정 + Q 번호(확인할 것에 같은 번호)
- 2번 «다르게 부르는 말」: README · 데이터 열 · 담당자가 같은 뜻을 다르게 부르면 모두 · 4번은 단위 · 시간대 먼저 · 🔒 개인정보 · 비밀값 열은 «쓰지 않음」 · 5번 «시점」은 시간 따라 바뀌는 연결만 · 6번 «나중에 바뀌나」를 비우지 않는다

**1-6. 검토 9개 — 걸리면 확인할 것으로**
- **1.** 거꾸로 따라간 길에 빠진 대상이 있나 **2.** 대상마다 «무엇이 같으면 같은 것인가」가 있고, 데이터에서 실제로 겹치나 **3.** 값 종류를 셌나 · 빈칸 · 이상한 값이 경우를 하나 더 만드나 · 중간 경우(모름 · 처리 중 · 보류)가 나중에 무엇이 되나 **4.** 연결마다 «하나에 몇 개」가 정해지나 · 시간 따라 바뀌면 어느 시각 기준인가 **5.** 두 출처의 모양(시간대 · 단위 · 구별 기준)이 같나 **6.** 분모가 «줄 수」인가 «대상 수」인가 **7.** 추정 줄마다 확인할 것에 같은 Q 번호가 있나
- **8.** 품질 숫자(불량률 · 수율)면: 분모가 검사한 수인가 투입한 수인가 · 홀드 · 재작업 · 재검사는 위 · 아래 어디로 · 불량 웨이퍼 수인가 결함 개수인가 · 첫 판정인가 최종 판정인가 · 설비별 비율의 평균인가 합계의 비율인가 · 기록 없는 기간은 0 인가 빠진 값인가
- **9.** 경계 장면을 하나 만들어 봤나(«일요일 밤 연마 · 월요일 검사는 어느 주?」 · «자정에 걸친 작업은 어느 날?」) — 답이 둘로 갈리면 확인할 것

**1-7. 확인할 것(맨 위 빨간 상자) — 질문 문장은 쓰지 않는다**
- 🔴 **확인할 항목만** 적는다. 담당자에게 보낼 질문 문장은 유저가 앞 답을 보며 직접 쓴다(AI 가 쓴 질문 묶음을 붙여 넣으면 «사소한 것부터 점점 깊게」 흐름이 안 보인다)
- 번호 Q1 ~ · 단계: 1 쉬움(업무 흐름 · 사실 · 데이터의 뜻)부터, 2 깊음(세는 기준 · 판단)은 그 뒤 · 같은 단계 안에서는 결과를 크게 바꾸는 것부터
- «답에 따라 바뀌는 것」은 말로(«처음 판정으로 세면 훨씬 높게 나온다」) — 숫자 폭은 8번 🔢 줄에. 비었거나 «바뀌는 것 없음」이면 지운다
- 데이터 · 명세로 알 수 있는 건 «먼저 직접 확인」 · 만드는 방법의 선택(화면 · 범위)은 «— 유저가 정함」 · 🔴 담당자 몫을 유저에게 묻지 않는다(짐작으로 답하게 된다)

**1-8. 만들 것 판정 · 한눈에**
- 만들 것 판정: README · 담당자가 꼭 요구 = ⭐ · 핵심 흐름을 살리고 싸다 = 🟢 · 요구 근거 없음 = 🟠(지우지 말고 «왜 안 하나」를 남긴다 — 범위 합의 재료) · 규칙 위반 · 요구와 반대 = 🔴(🔒 개인정보 · 비밀값은 늘)
- 0번 한눈에: 표 7줄(누가 · 무엇을 · 최종 결과 · 누구와 · 모르는 핵심 · 가장 큰 함정 · 지금 상태) — 데이터 과제면 «가장 큰 함정」 필수

**1-9. 마무리** — 4절 쉬운 말 검사(위 네 상자) · 지금 상태 숫자 맞추기 · 10번에 «초안」 · 커밋 «지도: 초안 — 확인할 것 N개」 · 채팅 보고는 한눈에 + 확인할 것 Q 번호 목록 + 다음 할 일 한 줄(«담당자에게 보낸 문장 · 받은 답을 붙여 줘»)

## 2. 갱신 — 담당자 답 · 유저 결정 · 새 데이터를 받았을 때

> 정해지는 즉시 고친다 — 나중에 몰아서 하면 다음 세션이 «아직 모른다」며 같은 걸 또 묻는다

- **2-1.** 유저에게 보낸 문장 · 받은 답 원문을 채팅에 붙여 달라고 해 docs/INTERVIEW.md 2절에 그대로(보낼 때 확인할 것 상태 📨) → 확인할 것 해당 Q 를 🟢 · 답 요지 한 줄
- **2-2.** 그 답이 바꾸는 칸을 모두 고친다 — 근거를 추정 → 담당자(시각) · 유저 · Q 번호 지우기 · 만들 것 판정도 다시
- **2-3.** 답 때문에 새로 생긴 애매함은 새 Q 번호로 · 새 데이터 파일이면 1-2 부터 다시
- **2-4.** 10번 바뀐 기록(시각 · 무엇 · 계기) · 이미 짠 코드 · 테스트에 영향이 있으면 docs/ADR.md 해당 섹션 «작업 중」 칸에 🔴 로
- **2-5.** 지금 상태를 맞추고 커밋 «지도: Q번호 반영 — 바뀐 칸」

## 3. 지도를 쓰는 곳

- 계산 코드 · 테스트 전에 3 구별 기준 · 6 경우 · 7 규칙 · 8 계산을 읽는다 — 테스트 이름에 규칙 번호를 붙이면 추적이 쉽다
- 결과 요약 문서의 «판단 근거 · 남은 확인 사항」은 7번 규칙 · 확인할 것 대기 Q · 만들 것 판정 🟠 에서

## 4. 쉬운 말 — 유저가 바로 읽을 수 있게

| 쓰지 않는 말 | 대신 |
|---|---|
| 엔티티 · 객체 · 클래스 · 인스턴스 | 대상 · 하나하나 |
| 식별자 · 기본 키 · PK | 구별 기준 |
| 속성 · 필드 · 어트리뷰트 | 정보 · 열 |
| 관계 · 릴레이션 · 카디널리티 · 1:N | 연결 · 하나에 몇 개 |
| 상태값 · enum · 도메인 값 | 경우 |
| 지표 · 메트릭 · KPI · 파생 값 | 계산 · 계산해서 나온 값 |
| 스키마 · 정규화 · 무결성 · 조인 | 표 모양 · 한 줄로 정리 · 빠짐 · 겹침 없음 · 붙이기 |
| 도메인 · 비즈니스 로직 | 업무 · 업무 규칙 |
| 중복 레코드 | 같은 대상이 여러 줄 |

- 데이터 열 이름 · API 경로는 원래 글자 그대로 쓰고 옆에 뜻을 붙인다 · 검사: 왼쪽 말이 남았는지 찾아(grep) 바꾼다

## 5. 전용 명령 — 유저가 담당자와 대화하는 동안 쉬지 않고 조사

- 🔴 유저가 «API 체크» 처럼 명령 이름만 말해도 바로 실행한다(AGENTS 1-7)
- «API 체크» — API 문서대로 curl 로 실제 호출 + 찔러보기(빈 값 · 틀린 키 · 없는 번호 · 아주 큰 값 · 같은 요청 두 번 · 느린 응답)
	- 읽기 호출부터 · 네트워크는 샌드박스 밖 승인이 필요하니 호출을 모아 한 번에 청한다 · 데이터를 바꾸는 호출은 유저 승인 뒤 · 키 값은 출력 · 기록하지 않는다(키 이름만)
- «DB 체크» — 읽기 전용인가 · 여러 곳이 동시에 쓰면 겹칠 수 있나 · 표 · 열 · 빈 값 · 중복 · 고유 · 연결 제약 · 크기
- «기타 체크» — CSV · 그 밖 파일의 특이사항(빈 칸 · 형식이 다른 줄 · 단위 · 날짜 형식 · 인코딩 · 이상값 · 중복) · 세는 법은 1-2
- «모두 체크» — 셋 다
- 결과를 적는 곳
	- 데이터 사실(빈칸 · 값 종류 · 중복 · 단위) → 해당 2 ~ 8번 칸의 🔢 줄(1-5)
	- 동작 사실(응답 코드 · 찔러보기 결과 · 읽기 전용 · 동시 쓰기) → 9번 출처 «주의» 칸 — 개발 지식 없는 사람이 읽을 말로 · 확인한 명령 · 시각을 근거로 같이 · 응답 코드는 풀이를 붙인다(401 = 열쇠(인증)가 없거나 틀림 · 404 = 그 주소 · 그 항목이 없음 · 429 = 너무 자주 불러 막힘 · 500 = 서버 쪽 오류)
	- 담당자에게 확인할 것이 나오면 «확인할 것» 에 Q 번호로(1-7) · 고친 칸은 2-5 처럼 커밋
