| 6 | v2 | 검증관 — 데이터 · 계산 · 재계산 | 첫 검증 | 새 서브 | worktree · 검증 기록 |

- **조사 서브(research)** — 유저가 확인 · 조사를 시키면(«~ 알아봐» · «최적화 알고리즘 찾아봐» 등 · 🔎 포함): 🔴 유저가 따로 말하지 않은 한 **내가 생각하거나 조사하지 않고 유저 글을 그대로 넘긴다**(내 부하를 안 늘리려고 · 2026-11-05 유저 지정)
	- 넘기기 = research 에게 `followup_task`(없으면 띄운다 · 온톨로지 중 자리가 없으면 먼저 끝나는 자리) → 유저에게 «조사 넘김» 한 줄 → 하던 일로 돌아간다 · 답을 기다리지 않는다
	- research 는 코드를 고치지 않고 · 결과를 docs/research/<주제>.md 에 쓰고 · 끝나면 알림 종(AGENTS 2-7 · `--to file:<경로>`) 으로 유저에게 직접 알린다 — 내 턴이 끝나 있어도 유저가 받는다
	- 결과를 코드 · 계획에 넣는 것은 유저가 정한 뒤 — 그때 hand_off 로

- **섹션 계획 서브(plan)** — 명세 쓰기를 내가 안 맡으려고 둔다(2026-11-05 유저 지정): impl 이 섹션 N 을 짜는 동안 plan 은 섹션 N+1 의 hand_off · 틀 채우기 · 설문을 준비한다
	- 🔴 **세부(함수 표 · 설문 · hand_off 섹션)는 한 섹션 앞까지만** — 멀리 앞서 쓰면 담당자 답 · 앞 섹션의 실제 코드로 틀어져 버리게 된다 · 앞 섹션이 끝나면 실제 함수 이름을 읽고 맞춘다 · 작업 뼈대(제목 · 요약 · 순서)만 «그려» 때 섹션 1 ~ 8 을 한 바퀴 그린다
	- 그래프 세 단계(뼈대 → 검증 → 살 · $graph 2절): «그려» → plan 에게 뼈대(impl 과 최대 2왕복 · 끝맺음 plan · 나는 긴 wait_agent) → 섹션 뼈대가 끝날 때마다 검증관에게 «이 섹션 검증 칸 채우기» → 유저가 «미논의 업데이트» 라고 하면 plan 에게 그 섹션 설문 · 살(코드 사실은 impl 에 한 번 묻는다 · 구현 중인 impl 에게 설문을 시키지 않는다)
	- 코드는 읽기만 한다(고치지 않는다) · 유저 결정은 hand_off 에 적힌 것만 믿는다 · 설문은 섹션마다 정말 필요한 것만(유저가 병목이 된다)
	- 구현 넘기기는 내가 한다 — 범위 승인이 유저 답에 달려 있어서 plan 이 impl 에게 직접 넘기지 않는다 · 섹션이 끝나면 impl 에게 다음 섹션 · plan 에게 그다음 섹션을 준다
- **구현은 한 줄기** — 병렬 구현 안 함 · 예외: 쓰는 파일이 안 겹치고 · 연결이 코드로 고정됐고 · 갈래마다 15분 넘는 분량이면 두 갈래까지
- **온톨로지 뒤 재배치**: A3 서브 → plan · A1 서브(합친 쪽) → fix · A2 서브 → test(같은 서브를 이어 쓴다 · 주소는 처음 이름 `/root/a3` 그대로) · 집필 W · A0 · A1 뒤 묶음 서브는 닫고 · impl 과 검증관 3개는 새 맥락으로 띄운다(검증관 강도 high) — 먼저 띄운 뒤 모두에게 첫 지시와 주소표를 준다
- **서브 부리기(Codex 0.163/0.164 실측)**
	- 쉬는 서브에게 일 주기 = `followup_task` · `send_message` 는 턴을 시작하지 않는다(일하는 서브에게 정보를 더할 때만)
	- 형제 서브에게 직접 `followup_task` 가능 · 주소는 `/root/이름` 전체 경로나 ID 만(`fixer` 는 내 자식으로 해석 · `../fixer` 는 오류) → 서브 첫 지시에 **주소표**를 넣는다(실제 이름으로 — 예: 구현 /root/a3 · 수정 /root/a1 · 성공 기준 /root/a2 · 검증관 /root/v1 · /root/v2 · /root/v3)
	- 🔴 내가 턴을 끝내면 서브 완료 · 메시지로 안 깨어난다 → 일이 남아 있으면 긴 `wait_agent` 로 턴 안에 머문다 · 짧은 반복 · list_agents 반복 금지
	- 🔴 유저 글 · 마법봉은 턴 중에 바로 들어와 `wait_agent` 를 깨운다(steer · «Wait interrupted by new input») → 그 글을 처리하고 서브가 남아 있으면 **다시 `wait_agent`**(안 그러면 서브가 도는 중에 턴이 끝난다)
	- 서브 ID 는 압축 뒤에도 · 4시간 18분 유휴 뒤에도 재사용 통과 → ID 표를 WORKLOG 에 남긴다 · `unknown` · `closed` · `notLoaded` 오류가 실제로 나면 그때 새로 띄우고 hand_off 를 읽게 한다
	- 서브의 스킬 목록에는 키트 스킬이 안 실린다 → 서브에게 `$insp` 처럼 부르게 하지 않는다 · 지시문에 파일 경로와 절(`~/.codex/skills/insp/SKILL.md` 2-2 등)을 주고 읽게 한다
- **서브 답은 한 줄** — «통과» 또는 «실패 · 재현 스크립트 경로» · 상세는 hand_off · tests 에 · 나는 코드 · diff 를 읽지 않는다
- **검증 지시는 고정 양식** — 섹션 번호 · 성공 기준 · 커밋 해시 · 볼 파일 · 축만 준다 · 구현 설명은 주지 않는다 · 첫 지시에 «~/.codex/skills/insp/SKILL.md 맨 위 · 0-2 · 0-3 · 2-2 를 읽고 그대로» 를 넣는다
- **검증관 축**: v1 요구 · 성공 기준 / v2 데이터 · 계산 규칙 · 경계값 / v3 처음부터 실행 · 화면 · 보안 — 민감 섹션 = 셋이 동시에 각자 축만(검증 노드를 축마다 하나씩 verify-add · 제목에 축) · 저위험 = 한 명이 전체(노드 하나)
- **검증 실패 왕복(나를 거치지 않는다)**
	- 검증관이 수정 서브(`/root/...`)에게 `followup_task` 로 노드 · 커밋 · 실패 기준 · 재현 명령만 직접 보낸다(이유 · 해결안 금지)
	- 수정이 끝나면 수정 서브가 `./kit graph --role main done <작업>` → 같은 검증관에게 새 커밋 · 대상만 보낸다
	- 재검증은 재현 스크립트만 다시 돌린다(새 리뷰 금지) · 같은 노드가 두 번 실패하면 검증관이 나에게 한 줄 → 유저에게 올린다
- **지적 등급**: 🔴 필수(성공 기준 위반 · 데이터 오염 · 크래시)만 수정으로 보낸다 · 나머지는 hand_off «개선 제안» 칸에만
- **검증관의 사본**: `git worktree add --detach <폴더> <커밋>` 으로 커밋 기준 사본에서 시험한다(구현 중인 코드를 안 보게) · 재현 스크립트는 작업 폴더 tests/ 에 커밋한다 · 데이터가 git 밖이면 사본에 링크가 필요할 수 있다
- **수정 서브**: 작업 폴더에서 끝난 섹션 파일만 고친다 · 구현 서브가 지금 쓰는 파일과 겹치면 그 섹션이 끝난 뒤로 미룬다(나에게 «미룸 · 노드 · 파일» 한 줄 → 섹션이 끝나면 내가 다시 준다) · 커밋 관문은 재현 스크립트 + 관련 시험만(CODE_RULE 11-1) — tests 전체는 구현 서브가 섹션 끝에 돌린다
- **성공 기준 시험 서브**: 섹션의 C 번호마다 tests/ 에 시험을 쓴다(tests/ 밖은 안 고친다) · 담당자 질문 준비(«확인할 것» Q 번호 목록) · 답 반영(ontology 2절)도 이 서브
- **질문 노드**: 놀고 있는 서브에게 답을 시킨다(`./kit graph --role 2nd answer-start · answer` — 역할 코드만 2nd · 답은 노드에) · 놀고 있는 서브가 없으면 먼저 끝나는 서브에게 줄을 세운다

## 1-9. 기존 코드가 들어 있는 과제(정찰 · 정본 순서는 $ontology 1-2 «기존 코드 저장소»)
- 기존 테스트 통과 ≠ 정답 · «무엇을 보고 무엇을 안 보나» 한 줄을 WORKLOG 에 · 성공 기준(C 번호)마다 결과를 직접 보는 테스트를 더한다
- 기존 스타일을 따른다(CODE_RULE 머리말)
- 예방: 기존 테스트만 보고 숨은 테스트에서 떨어진다

## 3-1. 목표를 검증 가능하게 · 자체 검증
- «버그 고쳐» → 재현 테스트를 쓰고 통과 / «리팩터» → 전후 같은 테스트 통과
- 단순 버그 · 동작 오류는 직접 잡는다 · 유저에게 넘기는 건 «의도와 다른 동작» 뿐 · 화면도 도구로 직접 실행 · 확인

## 3-2. 바깥에서 보이는 결과로 판정
- 내부 변수 · 상태가 아니라 응답 · 파일 · DB · 화면으로 판정한다(예: 재시도 3회 → 변수 값 ✗ · 가짜 서버가 받은 요청 3건 · 응답 503 · 중복 행 없음 ✓)
- «호출됐다 · 200» 만으로는 통과가 아니다 · 종료코드 0 + 입력 · 기대값이 맞는 증거(행 수 · 응답 본문 · 파일 내용)
- 예방: 테스트는 다 통과하는데 버그가 그대로다

## 3-3. 최종 검증은 실제로 한 바퀴
- 실제 입력 → 동작 → 출력을 한 바퀴 · 명령과 실제 출력(건수 · 결과 경로)을 WORKLOG 에
- 서버형은 유저 탭에서 0.0.0.0 으로 띄운 서버에 주요 경로 응답 코드 확인(curl 은 처음부터 샌드박스 밖 승인 — 안에서는 떠 있어도 접속이 막힌다 · /health 는 add_health 를 넣었을 때만) · 화면은 유저가 Browser 도구로 보고 알려 준다(Codex 는 화면을 못 본다 · 필요하면 스크린샷 요청)

## 3-4. 완료 보고 — 실행한 것 · 못 한 것
- 실행 명령 + 실제 출력(통과 · 실패 수) + 통과 커밋 해시 · «될 것» 금지
- 검증한 것 / 못 한 것을 나눈다 · 전체가 안 돌면 따로 돌 수 있는 부분을 돌린다(예: «pytest -q tests · 18 passed · a1b2c3d · 못 한 것: 실제 API — 키 없음»)
- 예방: 못 돌린 범위를 숨겨 미검증 코드가 «완료» 로 커밋된다

## 3-5. 재현 스크립트는 파일로
- 재현은 tests/test_대상_증상.py 로 저장 · 경로를 검증 기록에 · 고친 뒤 같은 스크립트로 전/후
- 비슷한 쉬운 입력 말고 실제로 실패한 입력 그대로
- 재현(RED)은 기대값이 틀려 failed 한 것만 · 준비 오류(error — import · 픽스처 · 오타)는 재현이 아니다 → 테스트부터 고친다
- 재현 테스트엔 «예상된 실패» 표시(xfail · raises=AssertionError · strict=True · CODE_RULE 13절) · 민감 섹션 버그는 재현 커밋(표시) → 수정 커밋(표시 뗌) · 마지막 커밋은 반드시 통과
- 검증관의 «통과» 는 받고, «실패» 는 검증관이 수정 서브에게 바로 넘긴다(1-7 · 나는 돌리지 않는다 · 오탐 · 해석 차이는 검증관 «확인 필요» 로 온다)

## 3-6. 형제 전수 점검 · 회귀 범위
- 버그 하나를 고치면 형제를 전부 확인: 같은 사전의 다른 키 · 그 함수의 모든 호출부 · 다른 분기 · 대칭 쌍의 반대쪽 → 보고에 형제 목록과 판정
- 회귀 범위 = 고친 층 + 그 층을 쓰는 위 층(외부 연결 · DB → 업무 처리 → 화면) + 고친 기능을 부르는 다른 경로
- 같은 결과를 내는 경로가 둘 이상이면(화면 표 · CSV 등) 필수 칸 목록을 테스트에 하나로 두고 모든 경로가 다 내는지 단언
- 예방: 하나 고치고 쌍둥이를 놓친다

## 3-7. 테스트 조건을 느슨하게 만들지 않는다
- 테스트를 지우거나 조건을 느슨하게 바꿔 통과시키지 않는다 · 기대값이 바뀐 건지 코드가 틀린 건지 먼저 가린다
- 즉석 스크립트도 기존 테스트 · 문서에 적힌 함정(멈추는 호출 · 화면 없는 환경)을 먼저 찾아 쓴다

## 3-8. 회귀는 관련 부분부터 · 전량은 지시 한 번만
- 관련 테스트만 지목해 돌린다(pytest 는 폴더 지정) · 관문의 tests 폴더 실행(CODE_RULE 11-1)은 전량에 안 셈
- 🔴 전체 회귀는 두 경우에만: 유저가 따로 시킬 때 · ready-end 때 — 둘 다 서브가 돌리고 무조건 병렬(pytest -n auto) · 시간이 오래 걸리니 검증 서브는 자기에게 할당된 검증만 한다(전체 회귀 금지 · 유저 지정 11/04)
- 전량은 «전량 돌릴까?» 제안만 · 유저가 시킨 그 한 번만 유효(지난 사례로 다음에 스스로 돌리지 않는다)
- 전량을 안 돌렸으면 보고에 «미검증 범위 있음» · 판정은 결과 문자열 + 종료코드 · 시간에 따라 바뀌는 테스트는 실제 경과 시간에 기대지 않는다
