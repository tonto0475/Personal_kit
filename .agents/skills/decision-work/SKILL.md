# decision-work — 결정 문서 섹션 작업 절차

사람 · 세션 이름은 $main · $insp 0-2(유저 · MAIN = 구현자 · INSP = 검증자 · 서브). 섹션 뼈대 8블록의 모양은 docs/ADR.md 양식 · 헷갈리는 블록만 docs/examples/ADR_example.md 에서 grep 으로 본다.

## 0. 시작
- 인자: 섹션 번호(예: 1-2). 없으면 묻는다. 검증자가 부르면 «verify 섹션번호» → 6절만 수행
- 읽기: docs/WORKLOG.md → docs/ADR.md 의 그 섹션 → docs/CODE_RULE.md(코드를 쓸 때) · docs/UI_RULE.md(화면을 만들 때)는 필요한 절만 grep -n(통째로는 main 0-1 에서 한 번) · 데이터 · 계산 섹션이면 docs/ONTOLOGY.md 3 · 6 · 7 · 8번
- 섹션이 없으면 만든다: 제목 줄 «## 번호 · 이름 — 저위험|민감» + 블록 8개(수정 범위 · 목표 · 성공 기준 · 배경 · 논의 내용 · 1회차 · 결과 정리 · 검증 기록 · 코드 개선 제안). 진행 기록 표에도 한 줄 · 1회차 «작업 전» 에 착수 전 훑기(AGENTS 1-2)로 나온 질문을 «🔴 #N 🤖 질문 — 추천» + 빈 답 칸으로 쓴다(설문 id «섹션 #N» 과 같은 번호)
- **세로 조각 먼저**: 섹션을 나눌 때 1-1 은 입력 → 처리 → 출력이 한 바퀴 도는 얇은 기능으로 잡는다(예: CSV 읽기 → 숫자 하나 계산 → 화면 한 줄). «DB 를 다 만들고 → 처리를 다 만들고 → 화면» 같은 가로 순서는 쓰지 않는다 — 시간이 모자라도 언제든 돌아가는 제출물이 남게
- 목표 블록은 개요만(요약 · 문제 · 원인 · 만들 것 / 안 만들 것 · 제약). 성공 기준은 따로 «❇️ 성공 기준» 표에 C1 · C2 … 로 하나씩 쓰고 «→ 검증 행»을 단다. 민감 섹션은 경계 9종(ref/CHECKSHEET.md 2-9)을 훑어 해당하는 것마다 C 하나

## 1. 논의 정리 · 수정 범위 승인 — 구현 전
- 가장 최근 «논의 내용 · N회차» 블록에 🔴 줄이 있으면: 그 항목에 기대는 작업은 하지 않고 유저에게 묻는다(하나라도 있으면 $survey). 기대지 않는 작업은 진행해도 된다
- 유저 답은 질문 바로 아래 빈 칸(«> > 🚹»)에 옮기고, 그 아래 «🟢 결정 — 내용(🚹 동의 · 지시 · 설문 선택)» 을 덧붙인다. 검토한 다른 안이 있었으면 바로 아래 «→ 버린 안: … — 이유». AI 가 해석했으면 «🤖 해석: … 다르면 알려줘». 옛 결정이 뒤집히면 옛 줄 끝에 «→ N회차에서 바뀜»
- 블록 색을 다시 판정한다: 🔴 줄이 남으면 decision-open + 제목 끝 🔴, 없으면 decision-done + 🟢
- **수정 범위 콜아웃**을 채운다: 파일마다 한 줄 «파일 — 바꿀 함수 이름들» · «자세히» 표(파일 · 클래스 · 함수 · 지금 하는 일 · 변경 전 동작 · 변경 후 동작 — 쉬운 말로) · «생성 예정 파일»(없으면 «없음» · 키트 양식에서 처음 커밋하는 파일과 그 파일이 기대는 것 — src/core/errors.py · tests/conftest.py · src/ui/theme.py + assets/fonts · run.sh · requirements.txt — 도 여기에). 기존 저장소면 그 저장소 스타일을 바꾸는 것도 범위에 적는다
- warning(주황 🟠)으로 두고 유저에게 승인을 청한다. **유저 답 줄에 «승인» 단어가 있을 때만** success(초록 🟢)로 바꾼다. 질문 · 의견이 오면 범위를 고치고 다시 청한다
- «승인» 으로 초록이 된 결정 문서를 커밋하고(설문 반영 커밋과 따로), 그 커밋 해시를 WORKLOG «기록» 의 «섹션 시작 커밋» 줄에 적는다(검증 범위의 기준점)

## 2. 구현 — 위험도로 단위를 나눈다
- 🔴 **수정 범위가 초록(승인)이 되기 전에는 구현을 시작하지 않는다**
- **저위험**(UI 객체 · 배치 · 스타일): 한 번에 구현 → 커밋
- **민감**(데이터 파이프라인 · 외부 API · DB 쓰기): 단계마다 구현 → 커밋 → 검증 요청(3절)
- 검증자가 민감 단계를 보는 동안 저위험 작업을 진행한다
- 범위 밖 파일 · 함수가 필요해지면 **스스로 등록**한다: 초록 줄은 두고 «🟠 변경 N · 파일 — 함수 · 이유(등록 시각)» 줄 + 빈 답 칸 «> > 🚹» 을 덧붙이고 콜아웃을 warning 으로 되돌린다 → 커밋 → 유저 «승인» 전에는 그 파일에 손대지 않고 다른 일을 한다
- 버그 수정(민감)은 재현 테스트 커밋 → 수정 커밋 두 번으로 나눈다. 재현 테스트에는 «예상된 실패» 표시($insp · $main 3-5)를 붙여 재현 커밋도 전체 테스트가 통과하게 한다. 마지막 커밋은 반드시 통과
- 커밋 메시지: «[섹션] 무엇 - 왜» · 문서도 같은 커밋 · 커밋을 합치지 않는다 · 파일은 이름으로 add

## 3. 검증 요청
- INSP 에 codex queue 로 보낸다(main 1-3 · 메시지는 작은따옴표): «$decision-work verify 섹션번호 · 단계 · 범위(섹션 시작 커밋..이번 커밋) · 볼 곳(파일)»
- queue 가 안 되면 같은 글을 유저에게 한 덩어리로 출력해 INSP 창에 붙여 넣게 한다

## 4. 검증 결과 처리
- 검증 기록 · 코드 개선 제안 블록을 읽는다
- 지적마다 검증자가 남긴 재현 스크립트를 **직접 실행**하고 판정한다: 실제 문제 / 맥락 부족 오탐 / 해석 차이
	- 실제 문제 → 고친 뒤 **같은 스크립트를 다시 통과** → 상세 기록의 조치 · 조치 일시를 채운다 · 🔴 필수 지적이면 INSP 에 queue «재검증 — 행 번호 · 커밋»(INSP 가 일치 🟢) · 그 밖은 MAIN 이 일치 🟢
	- 오탐 → 상세 기록 조치 칸에 «오탐 — 이유»
	- 해석 차이 → 현재 회차 «작업 중» 칸에 🔴 질문으로
- 지적은 모아서 처리한다. 단 **다음 단계가 지적받은 코드를 그대로 쓰면** 바로 고친다
- 검증 기록 블록 색: 미검증 · 불일치가 남으면 빨강, 모두 일치면 초록

## 5. 작업 중 발견 · 마무리 · 다음 회차
- 구현 중 결정이 필요한 것을 발견하면: 현재 회차 블록 «작업 중» 칸에 «🔴 무엇 — 추천» + 빈 답 칸, 블록을 빨강으로. 요청 밖 기능은 구현하지 않고 «⏸️ 제안» + «→ 이유»
- 섹션이 끝나면 차례로
	1. 성공 기준 표의 **모든 C 에 검증 행이 달렸나** 확인 — 없으면 확인 방법 칸에 «수동 — 이유»
	2. 결과 정리 블록(구현 / 개선 / 미구현 · 깨질 수 있는 곳 6칸 · 사람이 승인한 지점) · 진행 기록 표(통과 커밋 해시)
	3. 과제가 DECISIONS.md 를 요구하면 공식 네 칸(문제 정의 · 변경 계획 · 검증할 사항 · 남은 질문)에 이 섹션 요약을 한 줄씩 + «상세 → ADR 섹션 번호»(ADR 맨 위 대응표)
	4. WORKLOG 맨 위 «🔄 인계» 칸 갱신
	5. 커밋
- 유저 테스트에서 나온 버그 · 요청은 현재 회차 «작업 후» 칸에 적고 «→ N+1회차로». 다시 구현할 때는 옛 블록을 옮기지 않고 **«논의 내용 · N+1회차» 블록을 새로** 만든다. 수정 범위는 «❇️ 수정 범위 · N+1회차» 상자를 새로 만들어 다시 승인받는다(옛 상자 · 옛 🚹 승인 줄은 그대로)

## 6. 검증자 절차 («verify 섹션번호» 로 불렸을 때)
- **코드를 고치지 않는다.** 결정 문서의 검증 기록 · 코드 개선 제안 블록과 tests/ 의 재현 스크립트만 쓴다(필요한 줄만)
- 시작할 때와 단계 검증을 시작할 때마다 결정 문서의 그 섹션을 다시 읽는다
- 🔴 **테스트를 먼저 돌리고, 읽는 검토는 나중**: 이번 단계 관련 테스트 실행 → 결과 기록 → 그다음 diff · 연결된 함수 · 클래스 읽기 → 결정 문서 정책 · 성공 기준(C 번호)에 맞는지 검토 → 빠진 경우의 테스트 작성 · 실행. 같은 모델이 짜고 같은 모델이 읽으면 맹점이 같다 — 판정은 테스트 종료코드로
- **민감 섹션만** 서브 두 개를 병렬로: 리뷰 서브(아래 리뷰 질문으로 diff 를 읽고 지적만) + 테스트 서브(성공 기준마다 테스트 작성 · 실행). 둘 다 코드 수정 금지와 «실패한 테스트는 예상된 실패 표시(CODE_RULE 13절)를 붙여 tests/ 에 둔다 · 쓰는 중인 초안은 /tmp 에» 를 지시에 적는다. 합칠 때 판정 기준 = 테스트 결과, 리뷰 지적 = 더 확인할 후보. 저위험은 검증자 혼자 «테스트 → 리뷰» 순서
- **범위 대조**: 섹션 시작 커밋 이후 **구현자 커밋**이 바꾼 파일(git log --name-only 섹션시작커밋..이번커밋(요청에 적힌 해시) — 검증자 커밋 · docs 문서는 빼고)을 수정 범위 콜아웃 목록(변경 대상 + 생성 예정 + 승인된 변경 N)과 대조 → 상세 기록 «범위 대조» 줄. 목록 밖 파일이 있으면 불일치 🔴
- 판정 기준은 **$insp · $main 3-2 · 3-5 · 3-6 그대로** — 통과 인정 조건 · 바깥에서 보이는 결과 · RED 는 failed 만 · 재현 스크립트는 tests/test_대상_증상.py(경로는 상세 기록에) · 결함을 찾으면 형제 전수 판정
- 검증 정리표는 카테고리별(API · UI · DB …) · 행 번호 «카테고리-번호» · 내용은 자연어(코드 이름 없이). 상세 기록: 행 · 카테고리 · 대상 파일 · 대상 함수 · 기대 · 실제 · 일치(🔴/🟢) · 조치 · 조치 일시
- 코드 개선 제안: 대상 파일 · 카테고리(함수 · 클래스 · 패키지 구조 · 모듈화 · 분기·경계값 · 예외 처리 · 동시성·중복 쓰기 · 하드코딩) · 문제점(개선 방향은 쓰지 않음) · 중요도(🔴 필수 · 🟠 잠재 위험 · 🟢 있으면 좋음)
- 확신도 [확실 / 유력 / 의심] 을 붙이고, 버그가 없으면 «없음» · «확인했지만 문제없던 항목»도 적는다
- 실패 원인이 검증 범위 밖이면 git status 로 확인하고 그대로 적는다(디버깅하지 않음)
- 끝나면 검증 기록 · 개선 제안 · tests/ 를 경로로 커밋 → 요청한 세션에 queue «검증 끝 — 커밋 해시 · 불일치 N건»(insp 1-3)

### 6-1. 리뷰 질문 — «이 코드에서 ~ 는 확인했나?»
리뷰 서브 지시문에 그대로 넘긴다. ref/CHECKSHEET.md 2절 «어디서 깨지나» 표와 같이 본다.
- **함수** — 한 함수가 두 가지 일을 하지 않나? 이름과 하는 일이 맞나? 같은 입력에 같은 결과인가(숨은 전역 상태)?
- **클래스** — 여러 요청이 상태를 가진 객체 하나를 같이 쓰지 않나? 만들 때 외부 연결을 바로 열지 않나?
- **패키지 구조** — 화면 코드가 DB · 외부 API 를 직접 부르지 않나(CODE_RULE 3절 층 구분)?
- **모듈화** — 같은 계산 · 같은 규칙이 두 곳에 따로 있지 않나(한쪽만 고쳐질 위험)?
- **분기·경계값** — 0 · 음수 · 빈 목록 · 없는 키 · 최댓값 · 날짜 · 시간대 경계에서 어느 분기로 가나? else 가 조용히 삼키지 않나?
- **예외 처리** — 넓게 잡아 내부 오류를 외부 실패로 숨기지 않나? 실패 뒤 반쯤 된 상태(반쪽 주문 · 반쯤 쓴 파일)가 남지 않나? timeout 을 «실패»로 단정하지 않나(성공 · 실패 · 모름)? 오류 때 옛 결과가 화면에 남지 않나?
- **동시성·중복 쓰기** — (쓰기가 있고 중복 요청이 요구에 있을 때만) 확인과 쓰기 사이에 틈이 없나? 중복 금지 설정이 실제로 걸렸나? 같은 요청 두 번에 한 번만 쌓이나? 재시도가 처음과 같은 요청 구별 키를 쓰나?
- **하드코딩** — 주소 · 키 · 대기 한도 · 경로 · 임계값이 코드에 박혀 있지 않나(설정 파일 · 환경변수)?

## 편집 규칙
- 결정 문서는 필요한 줄만 고친다. 통째로 다시 쓰지 않는다
- 🚹 줄은 고치지 않는다(유저 답을 빈 칸에 옮기는 것만 예외)
- 결정 문서를 고친 뒤 바로 그 파일만 커밋한다
