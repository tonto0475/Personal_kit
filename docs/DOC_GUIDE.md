# DOC_GUIDE — 문서마다 무엇 · 언제 읽나 · 쓰는 법

> 세션 시작 때 역할 스킬(main · insp · 2nd)이 한 번 통째로 읽게 한다(그 뒤는 필요한 절만) · 압축 직후 훅이 다시 안내한다.
> 늘 지킬 규칙(금지)은 AGENTS.md 에, 쓰는 법 · 언제 읽나는 여기에 둔다(AGENTS 는 매 턴 실려서).

## 1. 문서 지도 · 별칭
유저는 파일 이름 대신 별칭으로 말한다.
- **AGENTS.md** = 전역 정책 — 자동으로 읽힘
- **docs/WORK_GUIDE.md** = 작업 가이드 · 작업 기준 — 무엇을 기준으로 일하나(12칸). 세션 시작 때 한 번 읽는다
- **docs/ADR.md** = ADR · 결정 문서 · 논의 문서 — 섹션을 구현 · 검증하기 전에 그 섹션을 읽는다. 쓰는 법은 $decision-work, 모양은 docs/examples/ADR_example.md
- **docs/WORKLOG.md** = 작업 기록 · 흐름 기록 — 세션 시작 · 압축(/compact) 직후 먼저 읽는다. 맨 위 «🔄 인계» 칸 · 모양은 docs/examples/WORKLOG_example.md
- **docs/CODE_RULE.md** = 코딩 문서 · 코딩 정책(코딩 · git) — 코드를 쓰거나 커밋하기 전에 읽는다
- **docs/UI_RULE.md** = UI 문서 · 프론트 정책 · 프론트 문서 — 화면을 만들거나 고치기 전에 읽는다
- **docs/INTERVIEW.md** = 인터뷰 문서 · 인터뷰 — 담당자에게 보낸 메시지 · 받은 답 원문 기록만(확인할 것 목록의 원본은 지도 맨 위 «확인할 것»)
- **docs/ONTOLOGY.md** = 데이터 지도 · 온톨로지 — 데이터 · 업무 규칙 · 담당자 질문의 원본. 데이터를 읽거나 계산 코드 · 테스트를 쓰기 전에 읽는다. 쓰는 법은 $ontology, 모양은 docs/examples/ONTOLOGY_ref_1.md(데이터 과제) · ONTOLOGY_ref_2.md(서비스 과제)
- **README_APP.md** = 우리가 만드는 앱 설명 · 실행법(run.sh) · 결과 정리 — 앱 설명은 여기 하나 / **docs/README.md** = 기존 저장소 정찰 구조표만($ontology 1-2 · 새 앱 과제면 비워 둠) / **루트 README.md** = 과제 지시문(수정 금지)
- **docs/surveys/<프로젝트>/** = 설문 기록(json · 화면은 devview 설문 탭) · **docs/examples/** = 문서 예시
- 예방: docs 문서는 자동으로 실리지 않는다 — 언제 읽을지 안 적으면 아무도 안 읽는다
- ADR = 무엇 · 왜 정본 / WORKLOG = 어떻게(흐름 · 파일 · 커밋 · 디버깅) · WORKLOG 에 옮긴 결정은 사본이라 고치지 않는다
## 2. 작업 기록(WORKLOG) 쓰는 법
- 맨 위 «🔄 인계» 칸(항목은 WORKLOG 틀)은 섹션이 끝날 때 · $hand-off 때 고쳐 쓴다. 다른 문서 내용은 베끼지 않고 경로로만
- 세션 시작 · 압축 직후 · 코드에 손대기 전: WORKLOG → ADR → 루트 README. 루트 README 가 과제 요구 기준선(업무 사실이 부딪히면 $ontology 1-2 정본 순서). 압축 요약만 믿지 않는다
- 예방: 작업에 집중하다 기록을 잊어 «무엇을 왜 했나»를 재구성하지 못한다 · 확정한 값을 다시 추측한다

## 3. 결정 문서(ADR) 쓰는 법
- docs/ADR.md 하나. 섹션 = 기능 · 작업 하나. ADR 맨 위 «작업 개요» 는 MAIN 이 과제를 받은 뒤 쓴다($main 1-1 의 5 · 섹션 목록 포함) · «읽는 법» 은 사람이 읽는 범례만 둔다 · 절차는 $decision-work
- 섹션 제목 줄 «## 번호 · 이름 — 저위험|민감»(저위험 = UI 객체 · 배치 · 스타일 / 민감 = 파이프라인 · 외부 API · DB 쓰기). 1-1 은 입력 → 처리 → 출력이 한 바퀴 도는 얇은 기능(세로 조각)
- 블록 8개: ❇️ 수정 범위 · ❇️ 목표(개요) · ❇️ 성공 기준 · ❇️ 배경 · ❇️ 논의 내용 · N회차(회차마다 블록 하나) · ❇️ 결과 정리 · ❇️ 검증 기록(접힘) · ❇️ 코드 개선 제안(접힘)
- **수정 범위**: 파일마다 한 줄 «파일 — 바꿀 함수 이름들» + «자세히»(표: 파일 · 클래스 · 함수 · 지금 하는 일 · 변경 전 · 변경 후) + «생성 예정 파일»(없으면 «없음»)
	- 색: 승인 전 warning(주황 · 제목 끝 🟠) → 유저 답 줄에 **«승인» 단어**가 있으면 success(초록 · 🟢). 다른 말(질문 · 의견)은 승인이 아니다
	- 승인 뒤 범위 밖 파일이 필요하면: 초록 줄은 두고 «🟠 변경 N · 파일 — 함수 · 이유(등록 시각)» 줄 + 빈 답 칸을 덧붙이고 warning 으로 되돌린다. 재승인 전에는 그 파일에 손대지 않는다
	- 회차가 바뀌면 «❇️ 수정 범위 · N회차» 상자를 새로 만든다 — 옛 상자 · 옛 🚹 승인 줄은 그대로 둔다(🚹 줄 불가침 · 이전 범위가 기록으로 남음)
- **성공 기준**: C1 · C2 …(C = Criteria · 기준) 번호마다 조건 · 동작 · 기대 결과 · 확인 방법 · → 검증 행(API-1 …). 저위험은 1~2줄 간단판, 민감은 다섯 칸 모두. 자동화가 안 되면 확인 방법에 «수동 — 이유»
	- 무엇을 C 로 삼나: 루트 README(과제 지시문) 문장 · 담당자 합의(INTERVIEW) · 데이터 지도 규칙에서 뽑는다 — 출처 없는 C 는 쓰지 않는다(요구 밖 기능 = 과구현)
	- 민감 섹션은 경계 9종(ref/CHECKSHEET.md 2-9)을 훑어 이번 변경에 해당하는 것마다 C 하나
- 논의 줄 상태(질문 줄 = «🔴 #번호 🤖 질문 — 추천» · 답하면 머리를 🟢 로): 🔴 논의 필요 · 🟢 논의 완료 · ⏸️ 보류(바로 아래 «→ 이유») · 질문 바로 아래 빈 답 칸 «> > 🚹» · 🚹 줄은 유저 전용
- 결정 줄 바로 아래 «→ 버린 안: … — 이유»(검토한 다른 안이 있었으면). 뒤집힌 옛 결정은 고치지 않고 줄 끝에 «→ N회차에서 바뀜»
- 상자 색: 그 블록에 🔴 줄 · 미검증 · 불일치가 하나라도 있으면 decision-open(빨강 · 제목 끝 🔴), 없으면 decision-done(초록 · 🟢). 회차마다 따로 판정
- 회차: «작업 후» 항목으로 다시 구현이 시작되면 옛 블록을 옮기지 않고 아래에 «논의 내용 · N+1회차» 블록을 새로
- 진행 표 기호: ⬜ 대기 · 🔄 진행 · 🟢 완료 · 🔴 논의 필요 · ⏸️ 보류 · ➖ 해당 없음
- 결정에는 출처(«🚹 지시 · 동의 · 설문 선택»)와 «→ 버린 안». 결정이 바뀌면 옛 줄을 고치지 않고 새 줄로 덧붙인다. 🤖 제안과 🚹 판단이 줄로 갈라져 보이게
- 과제가 DECISIONS.md 를 요구하면 ADR 맨 위 대응표대로 공식 네 칸에 요약 + «상세 → ADR 섹션 번호» — 섹션이 끝날 때마다 한 줄씩
- 기본 미리보기는 상자 색이 없으니 블록 제목 끝 점(🔴/🟠/🟢)을 항상 같이 단다
- 문서(ADR · WORKLOG)에 파일을 적을 때는 절대경로 대신 파일 이름(필요하면 저장소 안 상대 경로)만 — 대회 환경은 경로가 단순하다
- 예방: AI 제안과 유저 판단이 섞여 «누가 왜 정했나»가 안 보인다

## 4. 비밀값 확인 명령 — 키 이름 · 있음/없음만(값은 출력하지 않는다)

        grep -E "^[A-Z_]+=" .env | while IFS='=' read -r k v; do
            [ -n "$v" ] && echo "$k : 있음" || echo "$k : 없음"; done
