# A2 — README → contracts/reqs.json (4분)

**읽을 것**: 과제 `README.md` 전부 · `uploads/` 파일 이름 · 머리 줄 · 처음 몇 줄(읽기만) · `bookkit/contracts/README.md` 의 «reqs.json» 절 · 예 `bookkit/contracts/example/reqs.json`
**쓸 것**: `<책>/contracts/reqs.json` 하나(이어서 지도 칸은 맨 아래 절 — 지휘가 «이어서 지도» 를 보낼 때만)

## 할 일
1. **readme** — README 문장을 빠짐없이 한 줄씩 요지로(제출 · 실행 환경 · 제외 범위 포함). 묶음(`group`) 4개 안팎 — 만들 것 · 규칙 · 설정 · 제외 · 실행 환경 · 제출. 같은 group 은 붙여 쓴다(떨어지면 표가 둘로 갈린다) · 묶음마다 8행 안쪽 · 용어 각주는 `readme_fn`
2. **hidden** 8~12 — README 글에는 없지만 만들어야 하는 것. 자료를 열어 보거나 요구 두 개를 겹치면 드러난다. `where` = 어디서 드러나나(파일 · 숫자)
3. **silent** 7~10 — 요구를 다 읽어도 정해지지 않는 칸(목적 · 경계 시각 · 한도 · 실패 시 동작 …). `why` = 이 자료에서 왜 문제인가 2~3문장 · `default` = 답을 듣기 전 기본 가정 1문장
4. **questions** — 담당자에게 물을 것. 계획의 뼈대를 바꾸는 것 5~8개는 `"main": true`(3장 · 이 순서가 4장 선택표의 «질문 N»), 나머지 6~10개는 `false`(부록 B). 예 · 아니오로 답이 나오게 · `rec` = 답이 없을 때 쓸 기본 가정 · `opp` = 답이 반대면 무엇이 바뀌나(숫자)
5. **id** — 항목마다 `"id"`: readme `R1…` · hidden `H1…`(알고리즘 것을 먼저 적고 그 순서로 번호) · silent `S1…` · questions main `Q1…` / 부록 B `B1…`. 책의 번호가 id 숫자 그대로다 · 고칠 때 남은 id 는 바꾸지 않는다(새 항목은 다음 번호)
6. 분류(`cat`)는 화면 · 시스템 · 알고리즘 · 파이프라인 · 문서 — 파이프라인 = CSV 를 읽어 검사 · 정리 · 예외 처리 · 알고리즘 = 핵심 계산

## 숫자
- A1 · A3 와 동시에 일한다. 숫자는 손으로 적지 않는다 — `{F['이름']}` 자리를 두고 이름을 A1(자료 숫자) · A3(계획 숫자)와 맞춘다(지휘에게 «쓸 숫자 이름» 을 한 줄로 알려 둔다)
- 이름이 정해지지 않았으면 문장에서 숫자를 빼고 쓴다(집필이 채운다). 원문 인용(«12대» 처럼 README 에 적힌 값)은 출처를 붙여 그대로 써도 된다

## v3 서식(RULES 6절 «칸 길이표» — 검사기 «v3 한도» · «너무 짧다» 경고 0 으로)
- `hidden.text` = **짧은 구 28자 안**(«쓸 수 있는 OHT 는 12대뿐» · «OHT 한 대가 하루에 여러 건을 맡아야 한다») — 문장으로 길게 쓰면 1장 표의 «만들 것» 칸이 한 글자씩 줄바꿈된다 · `where` 55자(파일 · 숫자) · `make` 36자(명사구)
- `readme.text` 40자 · 묶음 4개 안팎(5개 이하) · 묶음마다 3행 이상(2행짜리 묶음은 옆 묶음과 합친다)
- `silent.title` = 한 줄 24자 안(v3 «무엇을 최소화하나(목적)») · `why` = 이 자료의 숫자를 넣은 2~3문장(35~150자) · `default` 60자
- `questions.why` · `opp` = 실측 숫자를 넣은 1~2문장(v3 31~124자 — «거점 배정이 계획의 뼈대» 처럼 한 구로 끝내지 않는다) · `rec` 은 «예.» 도 되지만 기본 가정이 따로 있으면 한 구 더(«아니오 — 지난달 수준(약 79%)으로 계획»)
- 예: `book_example/task09/task09_kit.html` 1장 표 · 3장 ◎

## 끝 신호
```
python3 bookkit/contracts/check_contract.py <책>/contracts/reqs.json
```
→ `PASS reqs.json` 한 줄 + 개수 보고. **A2 가 가장 먼저다** — PASS 가 나면 집필이 시작되고 지휘가 1차판(1 · 3 · 5장)을 낸다(cards/README.md «두 번 내보내기»). 2차판 빌드 전에 지휘가 셋을 함께 검사해 `{F['…']}` 이름을 맞춘다(없는 이름 = FAIL)

## 이어서 채울 온톨로지 칸 — 지휘가 «이어서 지도» 를 보내면
위 PASS 를 보고하고 멈춘다 → 지휘가 같은 서브(나)에게 `followup_task` 로 «이어서 지도» 를 보내면(A0 대조 결과 «확인할 것 후보» 가 있으면 그 지시에 실린다) README 를 읽은 맥락 그대로 한다(다시 조사하지 않는다 · 1차판 집필과 동시에 돈다).
**쓸 것**: `docs/ONTOLOGY.md` 위 네 상자(확인할 것 · 0 한눈에 · 만들 것 판정 · 1 README 풀이) — 처음이면 양식 칸 모양 그대로 두고 칸만 채운다 · 2 ~ 10번은 A1 · A3 칸(건드리지 않는다)

1. `python3 scripts/ontology/from_bookkit.py <책>/contracts --task <과제 폴더>` → `docs/ONTOLOGY_draft.md`(출발점 — 질문 → 확인할 것 · 요구 → R · 숨은 요구 → 만들 것 판정 · 초안 줄의 id 는 근거 칸에 남긴다)
2. **1 README 풀이** — 요구가 담긴 문장을 **전부 원문 그대로**(유저가 원문을 안 읽어도 보이게) · R = 과제 요구 · r = 과제 외 요구(시험 시간 · 써야 할 프로그램 · 제출 · 금지 도구 · 환경 — 2 ~ 9번에 안 옮긴다)
   - «어디로» 판정(처음 «예» 인 곳): 따로 이름 붙어 셀 수 있나 → 대상 / 둘이 어떻게 이어지나 → 연결 / 값이 될 수 있는 경우 → 경우 / 대상 하나를 설명하는 값 → 정보 / 계산해서 나오는 숫자 → 계산 / 늘 지킬 조건 · 금지 → 규칙 / 어디서 받나 → 출처 / 만들 결과물 → 지도 밖(결과물) / 일하는 방식 → 지도 밖(작업 방식) / 둘로 읽힘 · «사람마다 다르게 센다» → 확인할 것 · 한 문장이 여러 곳이면 모두
3. **확인할 것** — 🔴 질문 문장이 아니라 **확인할 항목만**(담당자에게 보낼 문장은 유저가 앞 답을 보며 직접 쓴다) · 번호 = 계약 id(Q · B · S) · 단계 1 쉬움(업무 흐름 · 사실 · 데이터의 뜻) → 2 깊음(세는 기준 · 판단) · 같은 단계 안은 결과를 크게 바꾸는 것부터
   - «답에 따라 바뀌는 것» 은 말로(숫자 폭은 8번 🔢) — 비었거나 «바뀌는 것 없음» 이면 그 줄을 지운다 · 데이터 · 명세로 알 수 있으면 «먼저 직접 확인» · 만드는 방법(화면 · 범위)은 «— 유저가 정함» · 담당자 몫을 유저에게 묻지 않는다
4. **만들 것 판정** — ⭐ README · 담당자가 꼭 요구 · 🟢 핵심 흐름을 살리고 싸다 · 🟠 요구 근거 없음(지우지 말고 «왜 안 하나» — 범위 합의 재료) · 🔴 규칙 위반 · 요구와 반대(🔒 개인정보 · 비밀값은 늘) · 근거 칸에 R · H id
5. **0 한눈에** 7줄 — 누가 · 무엇을 · 최종 결과 · 누구와 · 모르는 핵심(번호) · 가장 큰 함정(A1 뒤 지휘가 채운다 — 비워 둔다) · 지금 상태
6. 쉬운 말 — 위 네 상자에 `$ontology` 4절 표의 왼쪽 말(엔티티 · 식별자 · 관계 · 스키마 …)이 남았는지 grep 해서 바꾼다
