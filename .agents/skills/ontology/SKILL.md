# ontology — 과제 파악 책 + 데이터 지도(초반 한 번)

목적: 코드를 짜기 전에 유저는 책으로 과제를 빨리 정확히 파악하고, 에이전트는 지도에 «무엇을 확인하고 · 무엇을 만들고 빼며 · 데이터가 어떻게 이어지나」를 적는다.
- 책 = 유저용(bookkit/books/<이름> · 유저 자료의 주) / 지도 = 에이전트용 정본(docs/ONTOLOGY.md — 데이터 사전 · 업무 규칙 번호 · 담당자 답으로 확정된 값 · 만들 것 판정)
- 🔴 같은 분석 서브가 책 계약을 쓴 맥락 그대로 지도 칸을 **이어서** 채운다 — 다시 조사하지 않는다
- 이 스킬은 순서와 «누가 무엇을 이어서» 만 — 칸 쓰는 법은 카드(bookkit/cards/ A1 · A2 · A3 «이어서 채울 온톨로지 칸» · W1 ~ W6 · M) · 양식(docs/ONTOLOGY.md 읽는 법 · bookkit/README.md)
- 지도 채운 예시: docs/examples/ONTOLOGY_ref_1.md(데이터 과제) · ONTOLOGY_ref_2.md(데이터 없는 서비스 과제) · 책 예: bookkit/book_example/(task09/ · task10_guide_v3.html · 칸 예시 template_examples.md) · bookkit/contracts/example/
- 경로는 키트 폴더(AGENTS.md 가 있는 곳) 기준 · 명령의 python3 은 윈도우에서 py -3
- 목표: 1차판 + 지도 위 네 상자 = 과제를 받고 10분 안쪽 · 완벽보다 «확인할 것」을 빨리 꺼내는 게 먼저다
- ⭐ 책 품질 기준 = bookkit/book_example 의 09(task09/task09_kit.html · 펼침 사진 task09/Image/spread_*.png) · 10(task10_guide_v3.html · 펼침 사진 Image/spread_*.png) — 같은 수준으로 만든다

## 0. 독자 수준 — 책 · 지도를 이 수준으로 쓴다(유저 11/02 · 친구 리포는 이 블록만 교체)
- 개발 초보 — 컨테이너 · 도커 · 동시성 · 트랜잭션은 «처음 듣는 말» · 용어는 처음 나올 때 한 줄 풀이 · 입문 밖은 각주
- 알고리즘 지식 없음 — 풀이 후보는 이름보다 «무엇을 어떻게 가르나» 먼저 · 이름은 괄호 · 후보마다 «담당자가 이렇게 답하면 → 이 방안»
- 아는 것: 파이썬 간단 문법 · numpy · 영상 배열 개념 조금 · API · DB 아주 약간 · 공정 도메인 조금 → 이 범위의 말은 풀이 없이 써도 된다
- 난이도 기준: «README 를 안 읽고 이 책만 읽어도 결정할 수 있나» · 한 문단 5줄 이하 · 개념은 쉬운 경우 → 막히는 경우 → 이름 순서
- 결정이 걸린 곳은 «선택지 · 대가 · 추천 하나» — 유저는 결정만 한다(알고리즘 · 구조는 AI 몫)

## 1. 순서 — 누가 무엇을 이어서

**1-1. 지도 파일 · 칸 주인 — 동시에 써도 안 겹치게**
- 초안 = scripts/ontology/from_bookkit.py(출발점 — 질문 → 확인할 것 · 요구 → R · 숨은 요구 → 만들 것 판정 · 파일 · 열 머리 → 4 · 9번 · 함정 → 3 · 6번 · 사실 → 7번 후보) — A2 = docs/ONTOLOGY_draft.md · A1 · A3 = --out <책>/work/onto_A1.md · onto_A3.md(그때까지 나온 계약으로) · docs/ONTOLOGY.md 는 도구가 덮지 않는다
- docs/ONTOLOGY.md 는 A2 가 양식 칸 모양 그대로 처음 채운다(이미 채운 지도면 바꿀 칸만)
- 칸 주인: A2 = 확인할 것 · 0 · 만들 것 판정 · 1 / A1(합친 쪽) = 2 · 3 · 4 · 5 표 · 6 · 9 / A3 = 5 «가는 길» · 7 · 8 — 자기 상자만 패치 · 고치기 직전에 다시 읽기 · 패치가 문맥이 안 맞으면 다시 읽고 다시

- 서브는 커밋하지 않는다 — 1-9 에서 지휘가 diff 를 보고 그 파일만

**1-2. 기존 코드 저장소 · 데이터 없는 과제 · 정본 순서**
- bookkit 책을 만들지 않는 과제(데이터 없는 서비스 · 기존 코드 수정)면 계약 없이 A2 → A1 → A3 의 «이어서 채울 온톨로지 칸» 만 차례로
- **데이터 없는 서비스 과제**: 2 ~ 9번 대부분이 «해당 없음」이다. 칸을 지우지 말고 왜 없는지 한두 줄 · 대신 확인할 것 · 만들 것 판정이 본체다(ref_2)
- API 는 명세의 응답 예시로(근거 명세) · 키가 있으면 한 번 호출해 실제 값도 센다(읽기 호출만 · 키 값은 출력 · 기록하지 않는다) · DB 는 표 · 열 · 빈 값 · 중복 · 고유 · 연결 제약 · 크기를 센다
- **기존 코드 저장소** — 파일을 다 읽지 않는다
	- 정찰 6항목: 패키지 목록(requirements · package.json) · 프레임워크 · 진입점 · 상위 2단계 폴더 · 설정 · 테스트 위치 → 요청 하나를 진입점 → 입력 검사 → 업무 처리 → DB 까지 따라간다
	- 지도에: 대상 = DB 표 · 요청 / 구별 기준 = 중복 금지 설정(UNIQUE) · 요청 구별 키(없으면 그 자체가 확인할 것) / 경우 = 상태 값과 그 값을 정하는 코드 위치(파일 · 함수) / 출처 = .mcp.json · .env.example 의 서비스 · 키 이름(값 제외 · 키가 필요하면 바로 확인할 것)
	- 업무 규칙은 코드에서 짐작하지 않는다 — 코드에서 읽은 것은 근거 [코드] «지금 이렇게 동작한다» 일 뿐(기존 코드가 버그일 수 있다) → 규칙 칸에는 추정 + Q 번호
	- 정본 순서: 업무 사실은 담당자 답 → 루트 README → 저장소 문서(PRD · ARCHITECTURE 등) → 기존 코드 · 과제 지시(제출물 · 범위)는 루트 README · 부딪히면 혼자 고르지 말고 확인할 것에

## 2. 담당자 답을 받으면

계기 = 유저가 담당자 답을 채팅에 붙여 넣음(유저 결정 · 새 데이터도 같다). 정해지는 즉시 고친다 — 몰아서 하면 다음 세션이 «아직 모른다» 며 같은 걸 또 묻는다.
고치는 건 **MAIN 의 서브**(지휘는 지시 · diff 확인) — 책 칸은 그 카드를 쓴 서브가 살아 있으면 그 서브에게 이어서(followup_task) · 지도와 책을 서브 둘에 나누면 쓸 파일이 안 겹치게.

1. **지도에 반영** — 확인할 것 해당 줄 상태 🟢 · 받은 답 요지 / 확정값을 7 업무 규칙 · 2 ~ 6 · 9 데이터 사전 칸에(근거 추정 → 담당자(시각) · 번호 지우기) / 만들 것 판정 다시 / **답 원문은 10번 바뀐 기록 «계기» 칸에 그대로**(요약하지 않는다) / 답 때문에 새로 생긴 애매함은 새 번호 · 새 데이터 파일이면 A1 «이어서» 부터
2. **달라지는 곳 목록** — 이 답 때문에 바뀌는 곳을 줄마다 «곳 · 무엇이 바뀌나» 로: 책 숨은 요구(s1-H…) · 질문(s3-Q… · aB-B…) · 함정 처리(s2-T… · 부록 A) · 알고리즘 선택표(4장) · 숫자(numbers 이름) · flowtree 설문 · 노드(id) · 이미 짠 코드 · 테스트(→ docs/hand_off.md 해당 섹션 «작업 중» 에 🔴) — 목록은 지휘에게 보고(flowtree 설문 · 노드는 지휘가 flowtree 명령으로)
3. **책 새 판** — 계약 json 의 해당 항목(rec · default · opp · 숫자 · 단계 글)과 칸 파일을 고친다(항목 id 는 그대로) → check_contract.py PASS → build_book.py <책> --stage 2 --strict → 바뀐 블록에 «새로» 띠가 자동으로 붙는다 → 유저에게 경로(새 판 파일)
   - 판은 덮어쓰지 않는다 — 새 판 = 새 파일 `dist/<doc>__v<N>_<판 이름>.html`(자동 · 앞 판 html 은 그대로) · 유저가 결정을 틀어 방향을 바꾼 판은 `--label "<짧은 이름>"`
- 담당자에게 보낼 때 확인할 것 상태 📨 · 지도 커밋 «지도: 번호 반영 — 바뀐 칸»(책 폴더는 커밋하지 않는다)

## 3. 지도 · 책을 쓰는 곳

- 계산 코드 · 테스트 전에 3 구별 기준 · 6 경우 · 7 규칙 · 8 계산을 읽는다 — 테스트 이름에 규칙 번호를 붙이면 추적이 쉽다
- 결과 요약 문서의 «판단 근거 · 남은 확인 사항」은 7번 규칙 · 확인할 것 대기 번호 · 만들 것 판정 🟠 에서
- flowtree 는 ⑨ 준비판부터 쓴다(그 앞 과제 파악에는 쓰지 않는다 · 논의 뒤 보강 = `$graph` 논의 반영) — 책 스티커 답 = 2ND 서브가 bookkit/notes.py(bookkit/README.md «책 스티커»)

## 4. 쉬운 말 — 유저가 바로 읽을 수 있게

| 쓰지 않는 말 | 대신 |
|---|---|
| 엔티티 · 객체 · 클래스 · 인스턴스 | 대상 · 하나하나 |
| 식별자 · 기본 키 · PK | 구별 기준 |
| 속성 · 필드 · 어트리뷰트 | 정보 · 열 |
| 관계 · 릴레이션 · 카디널리티 · 1:N | 연결 · 하나에 몇 개 |
| 상태값 · enum · 도메인 값 | 경우 |
| 지표 · 메트릭 · KPI · 파생 값 | 계산 · 계산해서 나온 값 |
| 스키마 · 정규화 · 무결성 · 조인 | 표 모양 · 한 줄로 정리 · 빠짐 · 겹침 없음 · 붙이기 |
| 도메인 · 비즈니스 로직 | 업무 · 업무 규칙 |
| 중복 레코드 | 같은 대상이 여러 줄 |

- 데이터 열 이름 · API 경로는 원래 글자 그대로 쓰고 옆에 뜻을 붙인다 · 검사: 왼쪽 말이 남았는지 찾아(grep) 바꾼다

## 5. 하지 않는 것

- 🔴 책 구조를 바꾸지 않는다 — 장 파일의 «# ══ 구조» 아래 · kit.py · figs.py · contract.py · content/data.py · content/s4.py · content/apx.py · 장 · 블록 순서(빌드가 «구조 바뀜» 으로 알린다 · 더 필요하면 보고에 «양식 요청»)
- 🔴 숫자를 손으로 적지 않는다(계약 numbers · F['이름']) · 과제 원본(README · uploads · 제공 코드)은 읽기만 · 집필은 분석 스크립트를 다시 돌리지 않는다(계약 json 만)
- 🔴 담당자에게 보낼 질문 문장을 쓰지 않는다 — 확인할 것 항목 · 번호만 · 담당자 몫을 유저에게 묻지 않는다
- 스스로 시작하지 않는다(main 1-1 의 1 · 유저 호출) · 비유 · 다른 분야 상황 금지 · 책 폴더(bookkit/books/) · dist/ 는 커밋하지 않는다(.gitignore)
