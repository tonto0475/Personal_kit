# graph — 작업 그래프 그리기(준비판 · 논의 반영)

- 명령은 docs/flowtree.md 의 것만 쓴다(지어내지 않는다) · 예시: docs/examples/graph_example.md(그대로 돌아가는 명령 순서 + 완성 그래프)
- 서브가 쓸 땐 서브 목록에 키트 스킬이 안 실린다 → `$graph` 가 아니라 지시문에 이 파일 경로(~/.codex/skills/graph/SKILL.md)와 절을 준다
- 명령은 키트 폴더(AGENTS.md 가 있는 곳)에서 `./kit graph --role main <명령> …`(윈도우는 kit.cmd · 아래 표의 `fill` · `add` … 앞에 이것을 붙인다 · 한글 · 따옴표가 섞이면 `--args '<JSON>'` — AGENTS.md 3절)

## 1. 준비판 — 온톨로지 끝에 바로 만들 틀

언제 · 누가 · 순서 = 카드 bookkit/cards/P.md(`$ontology` 1-0 ⑨ · 2차판 시간에 영향 없게 A2 · A3 이 계약 · 지도를 끝낸 뒤 시작).

**세 칸 나누기** — 계획표(skeleton/plan.py) 항목마다 하나만

| 칸 | 기준 | 그래프에 |
|---|---|---|
| 바로 | 지도 «확인할 것» 에 안 걸리고 유저 결정도 필요 없다 | 작업 노드 + 함수 표 + 검증 노드 |
| 설문 하나면 됨 | 유저가 하나 고르면 시작할 수 있다 | 작업 노드 + 그 작업에 붙인 설문 노드 |
| 담당자 답 필요 | 지도 «확인할 것» 대기 번호에 걸린다 | 🔴 넣지 않는다 — 질문 목록(`<책>/work/graph_plan.md`)에만 |

- 그릴 곳 = 섹션0 틀 · 틀 작업 4칸을 위에서부터 채운다(넘치는 작업은 다음 섹션 틀로) · 설문 3 ~ 5개 · 첫 조각 = 입력 → 처리 → 출력이 한 바퀴 도는 얇은 세로 조각
- 맨 앞 설문 = «이 범위로 시작할까?» — 그 답이 hand_off 수정 범위 승인이다(main 1-5)

## 2. 논의 반영 — 논의가 끝나면 모아서 보강

맡는 쪽: MAIN 의 섹션 계획 서브(`main` 1-7 plan = A3 서브 · 구현 서브가 아니다) · 언제: 유저가 «논의 끝 · 그래프 그려» 할 때 · 담당자 답 · 유저 결정이 크게 쌓였을 때.

⭐ **세 단계로 그린다**(2026-11-05 유저 지정)

| 단계 | 언제 | 누가 | 무엇 |
|---|---|---|---|
| 뼈대 | «그려» 를 받으면 바로 | plan ↔ impl 논의 뒤 plan | 섹션 1 ~ 8 작업 칸의 제목 · 요약 · 순서만(함수 표 · 검증 · 설문은 아직) |
| 검증 | 섹션 뼈대가 끝날 때마다(구현 전) | 검증관 v1 ~ v3 | 그 섹션에서 뭘 검증할지 검증 칸을 `fill`(축마다 다른 칸 · 같은 항목을 겹쳐 쓰지 않는다 · 저위험 섹션은 검증관 한 명) |
| 살 | 유저가 MAIN 에게 «미논의 업데이트» 라고 할 때 | plan(코드 사실은 impl 에 한 번 묻는다) | 그 섹션의 설문 노드 · 함수 표 · 뼈대에서 부족한 곳 |

- 뼈대 논의는 **최대 2왕복**(`followup_task`) · 끝맺음은 plan 이 한다 · 그동안 MAIN 은 긴 `wait_agent` 로 턴 안에 있는다
- 설문은 유저가 요청할 때만 낸다(준비판 설문은 그대로) · 살은 한 섹션 앞까지만 · 구현 중인 impl 에게 설문을 시키지 않는다
- 아래 1 ~ 5 는 세 단계에 공통으로 쓰는 절차다 — 뼈대 단계의 «채우기» 는 작업 칸만

1. **모으기** — hand_off(전체 결정 · 🟢 결정 · 섹션 목록) · `inbox` 의 «설문 결정됨 · 설문 보류» · 지도 «확인할 것» 🟢 답 · graph_plan.md 질문 목록
2. **세 칸 다시** — 답이 온 항목을 1절 표로 다시 나눈다(아직 담당자 답이 없으면 그대로 질문 목록에)
3. **채우기** — hand_off 섹션 목록 순서대로 섹션마다 틀 작업 → 검증 → 설문 칸을 `fill` 로 채운다(3절) · 이미 채운 노드는 다시 쓰지 않는다
4. **고친 결정 반영** — 함수 표가 바뀌면 `funcs-set` · 결정으로 빠지는 작업은 `hold <작업> "hand_off 항목 번호로 뺌"`(에이전트 명령으로 지울 수 없다 · 제목도 못 고친다 → 제목이 달라지면 새 노드 + 옛 노드 hold · 지우기는 유저)
5. **닫기** — 반영한 설문마다 `survey-ack <설문> "무엇을 했나"` → `check` 로 «점검 정상» → hand_off «섹션 작업 순서» 표에 줄 덧붙임(`./kit handoff order-add <섹션> --plan "…"`) · 새 섹션의 수정 범위는 main 1-5 대로 승인

## 3. 명세

**섹션 배치**
- 섹션0 = 준비판 · 섹션 1 이후 = hand_off 섹션 순서(1-1 은 섹션0 의 첫 세로 조각을 잇는다)
- ⭐ 틀 = 모든 섹션 화면에 미리 깔린 빈 노드 — 작업 4개가 세로로 이어져 있고 작업마다 왼쪽 설문 2 · 오른쪽 검증 4. 노드를 새로 만들지 않고 틀 칸을 채운다
- 틀 id: `s<섹션>-t<1~4>`(작업) · `s<섹션>-t<k>-s<1~2>`(설문) · `s<섹션>-t<k>-v<1~4>`(검증) · 남은 빈 칸 = `frames <섹션>`
- 안 채운 틀은 Main · inbox · check · 알림에 안 나온다. 안 쓰는 칸은 그대로 두면 된다(지우지 않는다)
- 화면: 작업 · 파일 노드는 Main 에도 보이고 설문 · 검증은 섹션 화면에만 보인다 · 질문은 섹션(자기 칸 · 대상의 섹션)이 있으면 그 섹션에만, 없으면(섬 질문) Main 에

**틀 채우기**

| 종류 | 명령 | 어느 칸에 |
|---|---|---|
| 작업 | `fill s0-t1 --title "제목" --summary "…" --func "…" --doc "docs/hand_off.md#1-1"` | 입력 → 처리 → 출력 순서대로 위에서부터(첫 작업의 doc = hand_off 항목) |
| 검증 | `fill s0-t2-v1 --title "확인할 것" --script "tests/test_x.py"` | 바로 칸 작업 · 첫 조각의 끝 작업의 검증 칸 |
| 설문 | `fill s0-t3-s1 --title "질문" --option … --recommend N --why "…" --detail "…"` | 그 작업의 설문 칸 · 범위 설문 = 첫 작업의 s1 |
| 틀이 모자람 | 다음 섹션 틀로 넘긴다 · 꼭 더 필요하면 `add <작업> "제목" --section N` · `verify-add <작업> "…" --section N` · `survey-add <작업> "질문" --section N …`(`-` 금지 — 맨 위 설문은 다른 그래프로 간다) | |
| 뼈대로 이미 만든 묶음 | `./kit graph skeleton --section <섹션 번호> --bundles K0 K3 …`(`--section s2-t3` = 그 칸부터 · `--map K1=3` = 묶음별) | 새 노드 없이 그 섹션의 빈 틀 작업 칸을 위에서부터 `fill` → 완료 노드로 · 칸이 모자라면 다음 섹션 · 섹션 8 까지 없으면 실패로 남은 묶음을 보고. Main 에 붙일 땐 `--section <노드 id>`(그 노드 밑에 add) · 안 주면 «뼈대(skeleton)» 노드 밑 |

- 역할 코드 = `--role main`(서브도 같다) · 질문 노드는 만들지 않는다(유저 몫 · 명령 없음)
- 보류 풀기 = 구현을 시작할 때 `start`

**틀 밖 연결** — 틀 세로 줄에 없는 가지 · 틀이 모자랄 때만. 잇는 수단은 부모(`add` · `survey-add` · `verify-add` 의 첫 인자)뿐이다 — 에이전트가 선만 따로 긋는 명령은 없다

| 잇는 것 | 명령 | 그려지는 선 |
|---|---|---|
| 틀 칸끼리 | 없음 — `fill` 만 · 틀 선은 이미 있다 | 파란 흐름 선 · 위 작업 → 아래 작업 · 설문 → 작업 · 작업 → 검증 |
| 작업 → 작업(순서) | `add <앞 작업> "제목" --section N` | 회색 계층 선(앞 작업 오른쪽 → 뒤 작업 왼쪽) |
| 설문 → 작업 | `survey-add <작업> "질문" --option … --section N` | 회색 계층 선(작업 → 설문 쪽으로 그려진다 — 틀과 방향이 달라도 뜻은 같다) |
| 작업 → 검증 | `verify-add <작업> "확인할 것" --section N` | 보라 점선 화살표 |
| 질문 → 대상 | 에이전트 명령 없음 — 유저가 노드 «질문» 단추 · 손잡이 끌기로 만든다(`ask` · `link`) | 노란 점선 화살표 |
| 파일 노드 | 만드는 명령은 `file-add task_copy`(ontology ⓪ 에서 한 번 · Main 에 지급 파일 전부 · 다시 해도 안 늘어난다) · 잇는 명령 없음 — 작업에 파일을 걸 땐 `--doc 경로#앵커`(선 없음 · 자세히에서 열림) · 선은 유저가 손잡이를 끌어 긋는다 | 흰 점선(유저 선) |
| 섹션 사이 | 앞 섹션 작업을 부모로 `add s0-t4 "제목" --section 1` · 틀 칸끼리는 섹션을 넘겨 못 잇는다(`fill` 은 부모를 못 바꾼다) | 회색 계층 선 — 두 끝이 다 보이는 Main 에만 그려지고 섹션 화면에는 안 그려진다 |

- `--section N` 을 준다(안 주면 부모 섹션을 따른다) · 새 노드의 처음 자리는 화면이 틀 오른쪽 밖으로 잡는다 · 유저가 끌어 놓은 자리는 안 바뀐다
- 🔴 사슬로 잇지 않는다 — 설문 · 검증은 늘 작업에 직접 병렬로 붙인다. `verify-add <설문>` · `survey-add <검증>` 은 명령이 통과시키지만 쓰지 않는다(`verify-add <검증>` · `survey-add <설문>` 은 명령이 거부)
- 🔴 틀 칸이 남아 있으면 틀 밖 노드를 만들지 않는다 · `-`(맨 위)로 만들지 않는다

**제목 · 요약 · 함수 표**
- 제목 = 명사구 · 만들 것 이름(«요청 파일 읽기 · 검사 리포트») · 코드 이름 · 번호 없이
- 요약 = 60자 안(넘으면 명령이 거부) · «무엇이 되면 끝나나» 한 문장 + 묶음 표시(K1)
- 함수 표 = `--func "파일 | 함수 | 한 줄 설명 | ⭐"` 행마다 · 이름은 한글 임시 이름(계획표 그대로 · 구현 서브가 done 때 `funcs-set`) · ⭐ = 결정이 들어가거나 진입점 · 작업마다 1 ~ 3행
- 본문에 결정 · 이유를 쓰지 않는다 — hand_off 항목 번호로 건다(`--doc "docs/hand_off.md#1-1"`)
- 검증 글 = 바깥에서 보이는 결과 한 문장(«문제 줄이 있는 파일을 넣으면 리포트에 그 줄 번호가 나온다»)

**설문 문체**
- 질문 = 유저가 고를 수 있는 한 문장 · 쉬운 말(`$ontology` 4절) · 알고리즘 이름보다 «무엇이 어떻게 달라지나»
- `--option "라벨|풀이|장점;…|단점;…"` 2 ~ 3개 · 라벨 20자 안 · 풀이 한 문장 · 숫자는 책 · 계약의 값만
- 추천은 늘 하나(`--recommend`) · `--why` = 왜 이쪽인가 한 문장
- `--detail`(화면 «배경») = 짧은 문장 여럿으로 ① 무엇이 걸려 있나 ② 고르면 무엇이 달라지나 ③ 예시. 유저가 이 노드만 읽고 결정할 수 있어야 한다
- 🔴 설문 질문 · 선택지 · 배경 · 추천 이유에 항목 번호 · id · 약어(hand_off 1-1 · C1 · Q2 · S3 · H4 · R7 · K1 · D9)를 쓰지 않는다 — 그 번호가 가리키는 내용을 쉬운 말로 풀어 쓴다. 문서 링크는 끝에 덧붙일 수 있어도 설명을 대신하지 못한다
  - ❌ `--detail "hand_off 1-1 제안 6파일 8함수 · 제외 대기 Q1~Q7"`
  - ✅ `--detail "지금 범위는 입력 · 저장 · 계산 · 결과 표까지다. 정비 중 장비를 어떻게 다룰지는 담당자 답을 기다리느라 빠져 있다. 이 범위로 시작하면 첫 결과를 빨리 볼 수 있고, 빠진 것은 답이 오면 더한다."`
- 재료 = reqs.json 의 silent · hidden(유저가 정할 수 있는 것만)

**금지**
- 🔴 담당자 답이 필요한 항목을 작업 · 설문으로 넣지 않는다 · 담당자 몫을 유저에게 묻지 않는다
- 🔴 tree.json 을 직접 고치지 않는다 · `import-analysis` 로 요구를 통째로 올리지 않는다(준비판은 만들 것만)
- 🔴 없는 명령 · 옵션을 쓰지 않는다 · 코드에 없는 함수를 «완료» 로 두지 않는다(start · done 은 구현 때)
- 준비판은 틀 작업 4칸 · 설문 5개를 넘기지 않는다 — 넘으면 뒤 섹션 틀로 미룬다 · 승인 전 구현하지 않는다
