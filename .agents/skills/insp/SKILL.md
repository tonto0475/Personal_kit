## 1-3. 검증 왕복
- 시험 대상 = 지시의 커밋 · `git worktree add --detach <폴더> <커밋>` 으로 만든 사본에서 시험한다(폴더 = 저장소 밖 /tmp/<내 이름>-<커밋 앞 7자리> · 구현 중인 코드 · 미커밋을 안 보게) · 파이썬은 작업 폴더의 .venv · 데이터가 git 밖(.gitignore)이면 사본에 링크가 필요할 수 있다(ln -s) · 끝나면 git worktree remove <폴더>
- 재현 스크립트는 작업 폴더 tests/ 에 커밋한다(`./kit commit tests/test_….py` — 그 파일만 경로로 · 이름 tests/test_대상_증상.py 로 남과 안 겹치게) · hand_off 검증 기록 · 개선 제안도 작업 폴더에 — 셋이 동시면 자기 행만(패치가 실패하면 다시 읽고 다시 적용 — 공통 절)
- 실패 🔴 필수 → run <검증> fail → 수정 서브에게 followup_task 로 **노드 · 커밋 · 실패 기준 · 재현 명령만** 직접 보낸다(이유 · 해결안 금지) → MAIN 에게 «실패 · 재현 스크립트 경로» 한 줄
- 수정이 끝나면 수정 서브가 나에게 새 커밋 · 대상을 보낸다 → 새 커밋으로 사본을 다시 만들어 **재현 스크립트만** 다시 돌린다(새 리뷰 금지) → 상세 기록 일치 🟢 · 커밋 → run → «통과» 한 줄
- 🔴 같은 노드가 두 번 실패하면 수정 서브에게 보내지 않고 MAIN 에게 «두 번 실패 · 노드 · 재현 스크립트 경로» 한 줄(MAIN 이 유저에게 올린다)
- 지적 등급: 🔴 필수(성공 기준 위반 · 데이터 오염 · 크래시)만 수정으로 보낸다 · 나머지는 hand_off «개선 제안» 칸에만
- 🔴 예외 — 검증 칸 채우기: MAIN 이 «이 섹션 검증 칸 채우기» 를 주면 구현 전에 그 섹션의 뭘 검증할지 내 축으로 정해 `./kit graph --role main fill <검증 칸> --title "확인할 것" --summary "…"`(남은 칸 = `frames <섹션>` · 다른 검증관이 채운 항목을 겹쳐 쓰지 않는다 · 코드 · hand_off 는 안 고친다 · 끝나면 MAIN 에게 «채움 N» 한 줄)
- 예방: 저장소에 쓰는 서브가 늘면 같은 파일을 동시에 고쳐 충돌한다 → 내가 쓰는 곳은 위 세 곳뿐

## 1-4. 검증 단위 — 위험도

## 1-8. 시간 말고 실패 신호로 멈춘다

## 2-2. 검증 지시 · 판정(검증을 받으면)
- **코드를 고치지 않는다.** 쓰는 곳 = hand_off 검증 기록 · 코드 개선 제안 블록과 tests/ 재현 스크립트(필요한 줄만) · 검증 기록 행 · 상자 색 · 통과 커밋 · 재현 스크립트 줄은 `./kit handoff verify-log <섹션> <행> --result 통과|실패|대기 [--desc --file --func --expect --actual --action --commit --script]`(범위 대조 · 코드 개선 제안은 파일에서 직접) · 시작할 때와 단계마다 hand_off 그 섹션을 다시 읽는다
- 🔴 **테스트를 먼저 돌리고, 읽는 검토는 나중**: 관련 테스트 실행 → 결과 기록 → diff · 연결된 함수 · 클래스 읽기 → 성공 기준(C 번호)에 맞는지 검토 → 빠진 경우의 테스트 작성 · 실행 — 같은 모델이 짜고 읽으면 맹점이 같다 · 판정은 테스트 종료코드로
- **민감 섹션은** 검증관 셋이 각자 축 안에서 리뷰(2-3 질문으로 diff 를 읽고 지적만) + 테스트(성공 기준마다 작성 · 실행) · 규칙 = 코드 수정 금지 · 실패한 테스트는 예상된 실패 표시(CODE_RULE 13절)로 tests/ 에 · 쓰는 중인 초안은 /tmp · 판정 = 테스트 결과 · 리뷰 지적 = 더 확인할 후보 · 저위험은 한 명이 전체 «테스트 → 리뷰»
- **검증관 v2(데이터 · 계산 규칙 · 경계값)**: 계산 결과는 구현 코드를 보지 않고 규칙만으로 짠 독립 재계산으로 대조한다(차이 나는 칸이 버그 위치)
- **범위 대조**: git log --name-only 섹션시작커밋..이번커밋(검증자 커밋 · docs 는 뺀다)이 바꾼 파일을 수정 범위 콜아웃 목록(변경 대상 + 생성 예정 + 승인된 변경 N)과 대조 → 상세 기록 «범위 대조» 줄 · 목록 밖 파일이 있으면 불일치 🔴
- 검증 정리표 = 카테고리별(API · UI · DB …) · 행 번호 «카테고리-번호» · 자연어 · 상세 기록 = 행 · 카테고리 · 대상 파일 · 대상 함수 · 기대 · 실제 · 일치(🔴/🟢) · 조치 · 조치 일시
- 코드 개선 제안 = 대상 파일 · 카테고리(함수 · 클래스 · 패키지 구조 · 모듈화 · 분기·경계값 · 예외 처리 · 동시성·중복 쓰기 · 하드코딩) · 문제점(개선 방향은 쓰지 않음) · 중요도(🔴 필수 · 🟠 잠재 위험 · 🟢 있으면 좋음) · 확신도 [확실 / 유력 / 의심] · 버그가 없으면 «없음» · «확인했지만 문제없던 항목» 도

## 2-3. 리뷰 질문 — «이 코드에서 ~ 는 확인했나?»(리뷰할 때 그대로 · ref/CHECKSHEET.md 2절과 같이)

- **하드코딩** — 주소 · 키 · 대기 한도 · 경로 · 임계값이 코드에 박혀 있지 않나(설정 파일 · 환경변수)?
